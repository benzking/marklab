# 0007 · 运行日志落一份 `data/events.jsonl`

- 状态：已采纳（2026-11-02）
- 相关：0005（控制台模块）

## 背景

控制台「运行日志」原来只有四类**派生**事件：抓取队列（读 `data/tasks/`）、订阅命中
（读 `subs.allHits`）、智能标签（读 `tag-pending.json`）、判重（读 `duplicates.json`）。
派生出来的问题很具体：订阅调度器这一轮搜了什么、候选调度器把每条候选判成了什么、
下载队列此刻正在下哪个文件——这三件事只在内存里和 `lastResult`（**只留最近一轮**）里，
跑完就没了，页面上看不到，也没法事后查「这个模型为什么没进来」。

## 决策

1. **单一追加文件 `data/events.jsonl`**，不按子系统分文件。轮转和读取都只处理一个文件，
   五类事件落在一条时间轴上天然有序。
2. **轮转：单文件 5 MB，留 2 份**（`events.jsonl` + `events.jsonl.1`，写满覆盖最旧的）。
   日志是给人扫一眼的，不是审计；审计已经有 `data/tasks/*.jsonl`（永久保留，见 spec §4.7）。
3. **粒度**（实测一轮订阅 124 条候选，全记会淹没时间轴）：
   - 订阅调度器：每轮一条 `subs-run`（searched / candidates / matched / stopped / 耗时 / error）；
   - 候选调度器：只记**进队列**的候选，被挡的按 `decision` 汇总进同轮的 `subs-run`；
   - 下载队列：入队一条、**每个文件一条**、结束一条。
4. **智能标签、判重仍读各自落盘**（`tag-pending.json`、`duplicates.json`），不往事件流里重写。
   同一事实只存一处。

## 为什么不只派生

派生要求每个子系统都留下历史。`tasks/` 有历史，订阅只有 `lastResult`（最近一轮），
下载进度只有内存里的 `task.progress`。给这三者各补一套历史文件，等于三份轮转逻辑；
一份 append-only 的 jsonl 写完，读的时候合流。

## 代价

- 多一个写入点：订阅进程、任务进程都要 append。同一文件多进程 append，单行远小于
  `PIPE_BUF`，`appendFile` 打开即写不会撕裂；**不做文件锁**（同 ADR-0005 的口径：单机、低并发）。
- 5 MB 上限意味着高频事件会挤掉旧事件。按现在的量（一轮订阅约 20 行，一个模型约「文件数」行）
  能存几周；真要长期留，升级路径是按天分文件，不是加大单文件上限。
